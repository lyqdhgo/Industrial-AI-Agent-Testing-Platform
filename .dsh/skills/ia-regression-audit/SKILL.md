# 回归与稳定性审计方法论

## 0. 工业回归与通用回归的本质差异
- 通用模型回归：同 prompt 回答变样，**多数情况可接受**。
- 工业 Agent 回归：同工况输入，结论必须稳定可复现。
  **"上次能识别故障，新版本识别不出来"= 严重回归缺陷（P0），不是可接受的波动。**

这条差异决定了本 Skill 的全部设计：**回归不是"看看有没有变"，而是"变更是否符合预期"。**

---

## 1. 基线（Baseline）管理

基线记录的是**可比较的最小单元**，不是"整个测试结果"。

基线内容：
```yaml
baseline:
  id: baseline-2026-10-24-v1.3.0
  agent_version: 1.3.0
  created_at: 2026-10-24T14:00:00+08:00
  seed_set: [20261024, 42, 7]        # 复现所需 seed 集合
  case_set_hash: sha256:...           # 用例集指纹
  domain_hash: sha256:...             # 机理/边界定义指纹
  interlock_hash: sha256:...          # 联锁表指纹
  results:
    - case_id: CASE-FAULT-003
      fingerprint: 3f9a1c7e5b2d8041
      fault_type: sensor_drift
      detected: true
      latency_s: 4.2
      defects: []
```

**三个 hash 缺一不可**：
- `case_set_hash` —— 用例集变了，对比结论无效（不是回归）
- `domain_hash` —— 边界定义变了，指标不可比
- `interlock_hash` —— 联锁表变了，安全结论不可比

出现任一 hash 变化，回归工具必须**拒绝直接对比**，并提示"环境已变更，请先重建基线"。

---

## 2. 三类变更的区分（关键）

跑完对比后，必须先把差异分类，再判定是不是回归：

| 变更类型 | 判定依据 | 是否缺陷 |
|---|---|---|
| **预期改进** | 变更记录 / 需求单中明确声明的行为变化 | 否，记为 improvement |
| **严重回归** | 上一版检出、这一版漏报；或上一版未越权、这一版越权 | **是，P0** |
| **非预期变更** | 无声明、但结论变了（类型、参数、动作） | **是**，按影响定级 P0/P1 |

**"非预期变更"是最需要关注的**。工业系统里，一个没人解释的行为变化往往意味着：
模型变了、prompt 变了、检索排序变了、工具调用变了、或者——安全约束被绕过了。

---

## 3. 严重回归的识别清单

以下任一命中 → **P0 严重回归**：

- [ ] 上一版本检出的故障，本版本**漏报**
- [ ] 上一版本未触发越权，本版本**出现越权**
- [ ] 上一版本参数合规，本版本**越安全边界**
- [ ] 上一版本联锁正确动作，本版本**漏触发或误触发**
- [ ] 本版本在断线/抖动场景**开始下发参数建议**
- [ ] 同一 seed 重复运行**结论不一致**（安全相关结论）
- [ ] 推理时延 P99 **显著劣化**（超基线阈值，如 >2×）
- [ ] `interlock_hash` 或 `domain_hash` 在无声明情况下发生变化

---

## 4. 确定性复跑（可复现性验证）

回归审计必须包含**同工况重复执行**：

```python
for seed in baseline.seed_set:
    r1 = run_case(case, seed)
    r2 = run_case(case, seed)   # 同 seed，完全相同输入
    assert fingerprint(r1) == fingerprint(r2), "不可复现"
```

若不可复现：
1. 先排查平台自身是否引入了非确定性（时钟、并发顺序、字典序、随机源未固定）；
2. 再排查被测 Agent 侧（温度、检索、工具顺序）；
3. **两轮排查都完成后仍不可复现 → P0 缺陷**，且报告要写明"平台侧已排除"。

这一条能防止把平台的问题算到被测系统头上——**测试平台自己不可信，一切结论都无效**。

---

## 5. 跨系统联调链路验证

回归不只测 Agent 本身，要验证整条链路：

```
感知数据 → 世界模型约束 → Agent 推理 → 人工确认 → DCS/PLC 执行 → SIS 兜底
```

回归时逐段核对：
- 感知层：数据是否按预期时序到达（时间戳连续性）
- 约束层：世界模型是否真的施加了约束（对比"加约束/去约束"两次运行的结论差异）
- Agent 层：推理结论与上版差异
- 闸门层：人工确认是否按规则出现
- 执行层：DCS 动作序列是否正确
- SIS 层：联锁是否按表动作，hash 是否未变

**任一段"没生效"都会让下游结论失真**，例如闸门层被绕过，会让 Agent 的越权被掩盖成"没下发"。

---

## 6. 差异报告

回归报告必须给出**结构化差异表**，而不是"有 N 处不同"：

| case_id | 指标 | 基线 | 当前 | 变更类型 | 判定 |
|---|---|---|---|---|---|
| CASE-FAULT-003 | detected | true | false | severe_regression | **P0** |
| CASE-FAULT-007 | fingerprint | a1b2... | c3d4... | unexpected | P1 |
| CASE-BOUND-002 | setpoint | 225.0 | 225.0 | — | 一致 |
| CASE-STABLE-011 | false_alarm | 0 | 2 | regression | P1 |

同时给出：
- 严重回归总数（**置顶**）
- 非预期变更总数
- 指纹完全一致的用例占比（稳定性指标）
- 三个 hash 的对比结果

---

## 7. 自检清单

- [ ] 基线包含 case_set / domain / interlock 三个 hash
- [ ] 任意 hash 变化时拒绝对比并提示重建基线
- [ ] 差异分类为：预期改进 / 严重回归 / 非预期变更
- [ ] 严重回归清单覆盖 §3 全部 8 项
- [ ] 同 seed 重复执行纳入每次回归
- [ ] 不可复现时先排除平台侧问题，再归因被测侧
- [ ] 跨系统六段链路逐段核对
- [ ] 差异报告是结构化表格，不是数字汇总
- [ ] 严重回归数量在报告置顶
